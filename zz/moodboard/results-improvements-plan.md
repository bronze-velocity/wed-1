# Moodboard — Results Page Improvements

Concrete proposals for `components/moodboard/results/MoodboardResults.js` and friends. Written after reading the current results flow (`MoodboardResults.js`, `ResultCard.js`) and the wizard review step (`StepReview.js`).

Five things to fix, in order of user impact.

---

## 1. Button padding bug (quick win, do first)

Every button on the results page renders flush to its text because `.btn` in `app/globals.css:250` sets `display`, `border-radius`, transitions — but **no `padding`**. Only `.btn-lg`, `.moodboard-cta .btn-primary`, and a couple of one-offs get padding. Result: `Share this moodboard →`, `Send it →`, `Get my link →`, `Save changes →`, `This one excites me →`, `Share options →` all look wrong.

**Fix:** add a default `padding` to `.btn` in `app/globals.css`. Something like `padding: 12px 20px` (or the token equivalent — `var(--space-3) var(--space-5)`). Keep `.btn-lg` overriding to `15px 32px`. Audit the codebase for buttons that were compensating with inline padding and remove the now-redundant overrides (grep for `className="btn` + `padding`).

Not a results-page change strictly, but every button on this page is affected and the fix is one line.

---

## 2. Use AI a lot more — but only when the couple actually wrote something

Today the LLM produces `threeWords`, `whyItFitsYou` per match, and `hiddenMatches`. Everything else on the page is either a static template or a deterministic string join. The couple who wrote three paragraphs of custom story sees the same output shape as the couple who tapped through in 40 seconds.

Proposal: **branch the results page on whether the couple wrote anything of their own** (any `customEntries.*` non-empty, or any `story.*` filled). If they did, upgrade three things from deterministic to generated:

### 2a. Per-match rationale that quotes the couple back

`personalReasonFor(match.id, answers)` in `lib/moodboard/personalization.js` currently returns a canned "Because you picked <label>" line derived from ids. Replace (or supplement) this on the AI branch with a one-sentence rationale generated by the same `/api/moodboard/match` call, which:

- Quotes or paraphrases at least one custom entry or story sentence per match where a natural link exists.
- Falls back to the deterministic string when no plausible link (so it never invents connections).

This is essentially the "quote them back" instruction already sketched in `custom-pills-plan.md § How the custom entries get used`. Ship the results-page consumer alongside the prompt change.

### 2b. Reframed "three words" that leans on their sentences

Today `threeWords` is generated from all inputs. When custom text exists, instruct the model to prefer language that echoes it (e.g. `"Quietly. Proud. Ours."` if the couple wrote "quietly proud"). No new field — just tighten the prompt.

### 2c. NEW: AI-generated app suggestions section (see §3)

The rule: **AI-heavy output only when the couple gave the AI something to work with.** For a tap-only brief, keep today's shape — less risk of the LLM inventing texture the couple never mentioned.

**Wiring:** add a boolean `hasOwnWords` computed from `answers` in `MoodboardResults.js`, pass it through `results.matches` (already server-side, so compute in `/api/moodboard/match`). Render the two paths side-by-side while validating; kill the deterministic path once the AI path is trusted.

## 3. AI-suggested apps ("if you wrote your own words")

New section below `MatchedApps`, only when `hasOwnWords === true`. Not from the 20-app catalogue — genuinely new app concepts the model invents by reading what they wrote.

**Shape (per suggestion):**
- **Title** (3–5 words, sentence case)
- **One-line description** (≤20 words) — what guests do
- **Why it fits you** (1 sentence) — the specific phrase from their input it responds to

**Cap:** 2 suggestions max. Zero if the model can't find a plausible thread. Better empty than filler.

**Prompt slot in `lib/moodboard/prompts.js`:** a new `inventedApps` field on the JSON response, with a system-prompt instruction to only populate it when a custom entry or story sentence suggests an app that doesn't map to the existing 20. Each suggestion must cite the exact phrase it responds to (returned as a `sourceQuote` field) so the UI can render it as a receipt.

**UI:** a lighter-weight section header — *"Ideas we thought of while reading your words"* — with the two cards. Small `From what you wrote: "…"` line under each. No `Tell us you want this` CTA on these cards (they don't exist yet — a "Talk to us about this idea" button routes to the same email gate).

**Guardrails:**
- Suggestions must be genuinely new — the model should not restate one of the top 3 catalogue matches under a different name. Post-filter in the API route.
- If `inventedApps` is present but every entry duplicates a catalogue match, drop the section.
- Rate-limit unchanged; token budget bounded by the 10-custom-entry cap already discussed in `custom-pills-plan.md`.

## 4. "Three that feel like you" — improved cards + dynamic count

### 4a. Dynamic count with a cutoff

Today the section always shows 3 (`h2` says so; `matches.slice(0, 3)` implicit in the API). If the deterministic score for match 3 is weak, the third card dilutes the shortlist and undermines the "these actually fit you" promise.

**Proposal:**
- API returns up to 3 matches, but only those whose score exceeds a cutoff (e.g. ≥ 40% of the top match's score, or an absolute floor like ≥ 8 points — pick after eyeballing the scoring distribution in `lib/moodboard/scoring.js`).
- Section heading adapts: 3 → *"Three that feel like you"*, 2 → *"Two that feel like you"*, 1 → *"One that feels like you"*.
- If only 1 match clears the bar, add a short line under the heading: *"We'd rather show you one strong fit than pad it out."* — this earns trust and reinforces the "specificity" brand.
- Never show 0. If nothing clears the bar (shouldn't happen given the wildcard's +5 weight, but defensively), fall back to the top-scoring match with a softer heading (*"Closest to what you told us"*).

### 4b. Card improvements (`ResultCard.js`)

Current card is text-heavy with a phone scene hidden behind an "expand" tap. Suggested changes, ordered by impact:

1. **Show the phone scene by default** (or a small preview thumbnail of it) at the top of the card. The couple has read a lot of copy already — the room-payoff moment should be visible without a tap. Preserve the expand for full app description + actions.
2. **Rank pill is currently a small line of text** (`Best fit`, `Strong fit`, `Worth a look`) sitting above the title. Make it a small pill with the deterministic score visualized (e.g. a 3-dot meter or a subtle progress bar). "Strong fit" without any anchor to *how* strong is unfalsifiable copy.
3. **The `personal.label` line** ("Because you picked <label>") is doing the heavy lifting for the "we actually read your input" promise. When the AI-generated rationale from §2a is available, prefer it; keep the deterministic version as a receipt line below in smaller type (`Matched on: <picks>`).
4. **Actions row** currently only appears when expanded. Move the primary `Tell us you want this` CTA to always-visible at the bottom of the card. `See the full page` and the expand toggle stay where they are.
5. **Empty story handling.** If `answers.story` is empty and `personal` is null, drop the "Because you picked" line entirely rather than fall back to something generic — the card should look intentionally shorter, not broken.

## 5. Easy way to go back and edit/tweak

Currently once results render, the couple has no path back except browser back (which loses state? — worth verifying in `MoodboardWizard.js`). The `StepReview` step already has a clean `Edit in step ↗` affordance and an edit-in-place UX; we should surface a lightweight version of both from the results page.

**Two additions:**

### 5a. Persistent "Tweak your answers" affordance

A small button in the results header (near the `Share this moodboard →` CTA, but visually secondary): **`← Tweak your answers`**. Clicks route back to the wizard at `Step 7 (Review)` with all `answers` restored — the couple can edit any pill, delete anything, add a custom entry, and hit `Find our apps →` again. On re-submit, the results re-generate and replace the current view (with a small toast: *"Updated with your edits."*).

Wiring: `MoodboardWizard.js` currently transitions to results after `startMatching`. Add a `goBackToReview` callback down to `MoodboardResults` that sets `step = STEPS.length - 1` (the review step) and clears `results`. State is already held in the wizard.

### 5b. Inline edit on the answer strip

The `AnswerStrip` at the top of results shows every pill they picked. Make each pill removable with an ×, and add a `＋ Add` affordance at the end. Any change kicks off a debounced re-match (or shows a `Re-run with edits →` button — probably cleaner than auto-refetching, since the LLM cost is real). This is the "quick fix a typo / drop the one pill that felt wrong" path; deeper edits go through 5a.

Guard against runaway re-matches: cap at, say, 3 re-runs per session (client-side counter). After that, the button greys out with *"Tweak more in the review step."*

## Order of implementation

Ship in this order — each stage is standalone-useful and non-breaking:

1. **§1** — button padding fix. Half an hour.
2. **§4a** — cutoff logic + dynamic heading. Purely additive in the API + a heading swap. Half a day.
3. **§4b** — card redesign. A day; contained to `ResultCard.js` + a bit of CSS.
4. **§5a** — "Tweak your answers" back-jump. Half a day; a couple of wizard state changes.
5. **§2a + §2b** — LLM rationale + reframed three-words when `hasOwnWords`. A day, mostly prompt work + a `hasOwnWords` branch in the render.
6. **§3** — AI-invented app suggestions. Bigger: new JSON field on the response schema, prompt tuning to avoid duplicating catalogue matches, new card variant. 1–2 days.
7. **§5b** — inline edits on the answer strip. Last because re-matching from a partial edit is the trickiest UX to get right without confusing the couple. Half a day once §5a exists.

## What we deliberately don't do

- **Don't auto-refresh results when they edit.** The couple should see their edits land, then decide to re-run. Silent re-runs feel possessed.
- **Don't hide the deterministic top-3 behind the AI-generated rationales.** The receipt line (`Matched on: <picks>`) stays visible even when the AI writes the primary sentence. Otherwise the couple has no way to tell why an app ranked highly, and the "predictable ranking + LLM as copywriter" invariant from `custom-pills-plan.md` collapses.
- **Don't invent new apps for tap-only briefs.** The AI-suggested apps section is gated on the couple having written *something*. Without input, invention becomes filler.
- **Don't show a confidence percentage on the rank pill.** A 3-dot meter is legible and doesn't invite the "why isn't this 100%?" question a number does.
